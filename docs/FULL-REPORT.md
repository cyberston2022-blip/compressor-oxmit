## 1. خلاصهٔ اجرایی

**Oxmit** یک سرویس کامل فشرده‌سازی ویدیو در تلگرام است که روی یک VPS مشخصات زیر اجرا می‌شود:

| مورد | مقدار |
|---|---|
| سرور | AWS Lightsail — `18.227.142.205` (us-east-2) |
| مشخصات | 8 vCPU / 16GB RAM / 619GB SSD |
| سیستم‌عامل | Ubuntu 24.04.4 LTS |
| بات | [@Oxmit_bot](https://t.me/Oxmit_bot) |
| موتور فشرده‌سازی | **SVT Encore v1.0.0** (رسمی، ایمیج GHCR) |
| کانال آرشیو | `-1003732160424` (خصوصی، بات ادمین) |
| ادمین مالک | MohaMMad — `829999317` |
| دیپلوی | `/opt/oxmit` با docker compose (۷ سرویس) |
| دیتابیس | PostgreSQL 17 (کاربران، مدیا، کارها، آرشیو، تحویل‌ها، آمار) |

**چرا Local Bot API؟** Bot API ابری تلگرام محدودیت دانلود 20MB دارد — برای ویدیوهای چند گیگابایتی غیرقابل استفاده است. سرور رسمی `telegram-bot-api` (tdlib) روی همان سرور اجرا شده و **دانلود نامحدود** و **آپلود تا 2000MB** می‌دهد. بات از طریق پروسیجر رسمی `logOut` از API ابری مهاجرت کرده و فقط با سرور محلی کار می‌کند.

**سه لایهٔ Dedup** جلوی هدررفت CPU را می‌گیرد: تطبیق دقیق SHA-256، تجمیع درخواست‌های همزمان، و تشخیص ویدیوی مشابه با اثر انگشت بصری (pHash).

### 4.3 مدل داده (PostgreSQL)

| جدول | نقش | نکات کلیدی |
|---|---|---|
| `users` | کاربران | tg_id، ادمین، زبان، پروفایل پیش‌فرض، ask_each_time، سبک تحویل، thumbnail، بن |
| `media_assets` | هر فایل ورودی/خروجی | **sha256** (کلید dedup)، probe کامل JSONB، pHash، tg_file_id |
| `jobs` | هر درخواست | وضعیت (queued/processing/completed/failed/cancelled)، **stage**، progress، encore_job_id، input_params، profile_params، reuse_of |
| `job_requesters` | همهٔ منتظران یک کار | تحویل گروهی نتیجهٔ مشترک |
| `archive_records` | نتایج آرشیوشده | (source, profile, version) یکتا؛ message_id کانال، permalink، وضعیت active/no_gain/missing/blocked |
| `deliveries` | هر تحویل | روش (forward/copy/file_id/upload)، وضعیت، خطا |
| `counters` | آمار تجمیعی | ۱۵ شمارندهٔ اتمیک |
| `app_config` | تنظیمات runtime | کانال آرشیو، وضعیت توقف |

**ایندکس‌های حیاتی:** unique جزئی `(media_id, profile, version) WHERE status IN ('queued','processing')` — سپر cross-process در برابر encode تکراری + `pg_advisory_xact_lock(hashtext(...))` در تراکنش ثبت.

### 4.4 جریان زندگی یک درخواست

```
۱. کاربر ویدیو می‌فرستد (تا 4GB)
۲. کارت اطلاعات فایل (متادیتای تلگرام) + کیبورد پروفایل‌ها
   (اگر پروفایل پیش‌فرض داشته باشد و ask_each_time خاموش → خودکار)
۳. اعتبارسنجی: حجم/دیسک/سقف‌ها/بن/توقف
۴. دانلود لازم نیست — فایل از قبل روی دیسک سرور محلی است (فقط مسیر)
۵. SHA-256 استریمی + ffprobe + pHash (همزمان)
۶. Dedup:
   ├─ آرشیو فعال برای (sha, profile)؟ → تحویل فوری نتیجهٔ موجود
   ├─ کار فعال مشابه؟ → پیوستن به همان کار (advisory lock)
   └─ ویدیوی مشابه با اطمینان بالا؟ → بازیافت
۷. کپی به /media/incoming/<job>/ → ثبت در دوره (POST /encoreJobs, priority 50)
۸. ورکر فایل را برمی‌دارد → ffmpeg → خروجی در /media/out/<job>/
۹. poller (هر ۱۰ ثانیه) + کال‌بک دوره → پیشرفت روی پیام وضعیت (throttle 4s) + ETA
۱۰. SUCCESSFUL → اعتبارسنجی خروجی (ffprobe، مدت ±۱۵٪) → SHA-256 خروجی
۱۱. بررسی no-gain (خروجی ≥ ۹۸٪ منبع) و سقف 2000MB
۱۲. آپلود به کانال آرشیو (با thumbnail کاربر در صورت وجود) → ثبت message_id
۱۳. تحویل به همهٔ منتظران: forward → copy → file_id → آپلود محلی (یا document)
۱۴. پاک‌سازی پوشه‌های موقت + به‌روزرسانی شمارنده‌ها
```

### 4.5 مکانیزم‌های مقاومتی
- **بازیابی پس از restart:** کارهای بدون encore_job دوباره ثبت می‌شوند؛ کارهای در جریان با دوره reconcile می‌شوند
- **تشخیص گیر:** بدون تغییر پیشرفت به مدت `STUCK_MINUTES=90` → لغو + retry
- **ترمیم خودکار دومرحله‌ای سورس آسیب‌دیده:** خطای mux → retry با `fflags +genpts+discardcorrupt` → در تکرار بعدی → پروفایل `repair` (aresample async)
- **retry محدود:** TRANSIENT_CATEGORIES با backoff؛ خطاهای دائمی retry بی‌پایان نمی‌شوند
- **محافظت دیسک:** رد درخواست زیر 40GB آزاد، توقف خودکار زیر 20GB، ادامهٔ خودکار پس از رفع
- **پاک‌سویپ هر ۱۰ دقیقه:** فایل‌های موقت بالای ۲۴ ساعت (کارهای فعال مصون)

### 5.1 اجزا

### 5.2 پروفایل‌های فعال

| key | کدک | تنظیم کلیدی | کاربرد | اندازه‌گیری واقعی (۶۰ثانیه 1080p، منبع ۵۵MB) |
|---|---|---|---|---|
| `balanced` | H.264 (libx264) | CRF22, preset faster | پیش‌فرض متعادل | ~60-90s → 44.9MB (-19%) |
| `highq` | H.264 | CRF19, faster | حفظ کیفیت | 63s → 58.5MB (بدون صرفه*) |
| `small` | HEVC (libx265) | CRF27, faster | حجم کمتر | 93s → 36.0MB (-35%) |
| `maxcomp` | HEVC | CRF30, medium | کمترین حجم | 133s → 22.3MB (-59%) |
| `tgcompat` | H.264 High | CRF22, veryfast + faststart | حداکثر سازگاری | 33s → 39.9MB (-28%) |
| `r1080`/`r720`/`r480` | H.264 | عرض 1920/1280/854 | کاهش رزولوشن | 58s/28s/23s → -19%/-81%/-92% |
| `custom` | H.264 | بیت‌ریت محاسبه‌شده از حجم هدف (SpEL) | حجم دلخواه | هدف 5MB → 5.19MB ✓ |
| `repair` | H.264 | balanced + `aresample=async=1:first_pts=0` | ترمیم سورس آسیب‌دیده | — |

\* منبع مصنوعی testsrc2 بود؛ محتوای واقعی معمولاً صرفهٔ بیشتری نشان می‌دهد.

**همهٔ پروفایل‌ها:** `pix_fmt yuv420p` + `movflags +faststart` + صدای AAC (کدک پیش‌فرض ایمیج رسمی؛ libfdk_aac در ایمیج‌ها نیست) + بدون بزرگ‌نمایی (گارد سمت بات: `resolve_variant` کوتاه‌ترین ضلع منبع را با هدف مقایسه و در صورت کوچک‌تر بودن، پروفایل را تنزل می‌دهد).

### 5.3 لایه‌های Dedup (جزئیات)

1. **دقیق (Layer A):** SHA-256 استریمی از فایل روی دیسک (بدون دانلود مجدد — Local Bot API فایل را از قبل روی دیسک دارد) + پروفایل + نسخه → جستجوی `archive_records` فعال
2. **در حال انجام (Layer B):** `pg_advisory_xact_lock(hashtext(sha:profile:v))` در تراکنش + ایندکس یکتای جزئی → درخواست همزمان به‌جای encode تازه به کار موجود **می‌پیوندد** و در پایان نتیجه به همهٔ `job_requesters` تحویل می‌شود
3. **مشابه (Layer C):** pHash (ahash 8×8، ۸ فریم نمونه‌گیری‌شده در زمان ثبت — sync) + پنجرهٔ مدت ±۲ ثانیه + آستانهٔ سخت‌گیرانه (میانگین ≤۵ بیت، بیشینه ≤۱۲ از ۶۴) فقط علیه نتایج آرشیوشده؛ عدم تطبیق → encode عادی. نکتهٔ مستند: این لایه **ویدیو** را مقایسه می‌کند (صدا در آن نیست)

### 5.4 زنجیرهٔ تحویل و آرشیو
- کپشن استاندارد آرشیو: نام (پاک‌سازی‌شده)، پروفایل، رزولوشن، کدک، مدت، حجم قبل/بعد، درصد، کد کار
- تحویل: `forward` → در خطا `copy` → در خطا `file_id` → در نهایت آپلود محلی؛ حالت document از تنظیمات کاربر
- رکورد گمشده (پیام حذف‌شدهٔ کانال) → علامت `missing` + شمارنده + اطلاع ادمین؛ لینک داخلی کانال هرگز به‌عنوان لینک عمومی به کاربر نمایش داده نمی‌شود
- سیاست no-gain: خروجی ≥ ۹۸٪ منبع → نسخهٔ اصلی تحویل + رکورد `no_gain` (برای بازیافت‌های بعدی همان فایل)

## 7. مشکلات فعلی

### 7.9 🟢 حل‌شده — Permission denied بازگشایی روی فایل‌های جدید (2026-10-25)
- **علائم:** `ffprobe failed: ... Permission denied` روی فایل‌های تازهٔ کاربر (file_2 تا file_5)؛ فایل‌های قدیمی پس از chmod دستی سالم بودند.
- **ریشه:** tdlib فایل‌های دانلود را با مود **0640** (owner rw، group r) می‌سازد؛ umask فقط بیت حذف می‌کند و نمی‌تواند read-other اضافه کند — راه‌حل قبلی (umask 022) ناکافی بود.
- **فیکس ساختاری:** کانتینر bot-api با **uid 1000** (همان UID کاربر کانتینر بات) اجرا می‌شود (`USER 1000` در Dockerfile) + chown یک‌بارهٔ volume به 1000:1000. فایل‌های جدید مالکشان خود بات است — حتی 0600 هم خوانا می‌بود. Worker ها (root، mount ro) هم می‌خوانند ✓.
- **تأیید:** پروسهٔ bot-api = uid 1000 ✓، فایل ساخته‌شدهٔ جدید mode 644 owner=1000 ✓، بات file_5 را می‌خواند ✓، worker می‌خواند ✓، session بات پس از تغییر UID سالم ماند ✓.

### 7.10 🟡 باز — مسیر MTProto (آپلود >۲۰۰۰MB با اکانت شخصی)
پیاده نشده — نیازمند کد ورود تلگرام (تصمیم مالک) و مرور امنیتی. جایگزین فعال: تحویل چندپارته (بخش ۸.۲).

### 7.1 🟢 حل‌شده — سورس آسیب‌دیدهٔ ۱۱.۵ ساعته (کار `a93601e0`)
- **علائم قبلی:** ffmpeg همیشه در دقیقهٔ ~۳۴.۶ محتوا با `Error muxing a packet (-22)` روی استریم AAC متوقف می‌شد (هشدارهای decode: `illegal reordering_of_pic_nums_idc`).
- **روش عیب‌یابی (طبق دستور مهندسی):** دستور دقیق ffmpeg از لاگ INFO دوره (`FfmpegExecutor` خط ۱۱۷ دستور را کامل لاگ می‌کند) استخراج شد و با تست دستی موفق مقایسه شد.
- **ریشهٔ اثبات‌شده:** تفاوت نسخهٔ ffmpeg بود — ایمیج رسمی `encore-worker` نسخهٔ **8.1** را باندل می‌کند و muxer آن روی پکت‌های صوتی این سورس در نقطهٔ مشخص EINVAL می‌دهد؛ **همان دستور دقیق با ffmpeg 7.0.2 کامل و بدون خطا اجرا می‌شود** (تست ۴۰ دقیقه‌ای محدود و اجرای کامل تأیید شد). تست اسپن (بازهٔ ۳۴-۳۶ دقیقه) در هر دو نسخه پاس می‌شد → مشکل تجمعی/نگرش سخت‌گیرانهٔ نسخهٔ 8 بود نه محتوای آن نقطه.
- **فیکس پایدار:** ffmpeg استاتیک پین‌شده در `deploy/wrapper/` و mount روی `/usr/local/bin/ffmpeg` داخل ورکرها در compose. ffprobe/MediaInfo ورکر 8.x می‌مانند (فقط ffmpeg جایگزین شد).
  - **تصحیح (2026-11-01):** نسخهٔ واقعی باینری پین‌شده **Debian 7.1.5-0+deb13u1** است (SHA-256 `e7e7fb30…` — همان فایل ثبت‌شده در notices)؛ ارجاع‌های «7.0.2» در این سند تاریخی‌اند. نکتهٔ مهم‌تر: از 2026-11-01 مسیر ورودی توکن‌دار هرگز به Encore پاس داده نمی‌شود (hardlink در `/media/incoming/<job>/`)، پس این نشستی اصلاً مسیر توکن را نمی‌بیند.
- **نتیجه:** کار واقعی کاربر از نقطهٔ شکست رد شد (۷٪+، صفر خطای mux) و تا اتمام کامل ادامه داد.

### 7.2 🟠 سقف 2000MB خروجی تلگرام
Local Bot API آپلود بیشتر از 2000MB را نمی‌پذیرد. خروجی‌های بزرگ‌تر: کار کامل، فایل ۲۴ ساعت روی سرور، ادمین مطلع، کاربر پیام توضیح می‌گیرد. راه‌حل‌های ممکن: تقسیم خروجی به پارت‌ها (قابل پیاده‌سازی)، یا لینک دانلود HTTP موقف با توکن (نیازمند تصمیم دربارهٔ امنیت/عمومی‌کردن پورت).

### 7.3 🟠 no-gain روی منابع از پیش فشرده
ویدیوهایی که قبلاً خوب فشرده شده‌اند (مثل کار ۳ ساعته کاربر) خروجی بزرگ‌تری می‌دهند → کاربر «نسخهٔ اصلی» را پس می‌گیرد. این **طبق طراحی** است (هیچ فایل بدی تحویل نمی‌شود) اما انتظار کاربر را باید مدیریت کرد (پیام توضیح داده می‌شود).

### 7.4 🟡 کندی HEVC
libx265 روی CPU روی این سرور ~۰.۵× realtime برای 1080p است؛ `maxcomp` برای فیلم‌های طولانی بسیار کند است.

### 7.5 🟡 سقف سخت CPU
۸ vCPU با ۲ ورکر × ۳.۵ هسته = هر encode حداکثر ~۳.۵ هسته؛ throughput کل سیستم به CPU گره خورده است (بخش ۸).

### 7.6 🟡 صدا و زیرنویس
فقط اولین استریم صدا حفظ و به AAC استریو تبدیل می‌شود؛ زیرنویس‌ها و صداهای چندگانه در خروجی نمی‌آیند (محدودیت شکل job دوره 1.0).

### 7.7 🟡 تک‌سرور = نقطهٔ اتکای واحد
PostgreSQL/Redis بکاپ دارند اما سرویس روی یک VM است؛ خرابی سخت‌افزاری = downtime تا بازسازی (راهنمای بازسازی نوشته شده).

### 7.8 ⚪ موارد رفع‌شده (برای سابقه)
لیست کامل در بخش ۲ فاز ۴ — مهم‌ترین‌ها: دسترسی root-only فایل‌های tdlib، binding Map پیکربندی Spring از env، فیلدهای اجباری پروفایل 1.0، صف priority، و باگ بحرانی ثبت‌نشدن درخواست‌کنندهٔ اصلی در job_requesters (تحویل هرگز اجرا نمی‌شد).

## 8. چگونه سرعت را بالا ببریم؟

### 8.1 فوری و رایگان (فقط تنظیمات)

| اقدام | جزئیات | انتظار |
|---|---|---|
| **ورکر بیشتر با CPU کمتر برای هرکدام** | `WORKER_REPLICAS=3-4` و سقف CPU هر ورکر ~2.5 | throughput کل بیشتر (۳-۴ encode همزمان)، اما هر encode کمی کندتر. برای صف‌های شلوغ بهتر است |
| **پریست سریع‌تر برای پروفایل‌های کم‌کیفیت** | r480: `superfast`، tgcompat: `superfast` | ~۳۰-۵۰٪ سریع‌تر با افت کیفیت نامحسوس در رزولوشن‌های پایین |
| **SHA-256 حین کپی** | ادغام hash+copy در یک پاس خواندن (الان فایل ۲ بار کامل خوانده می‌شود) | برای فایل ۴GB حدود ۱۵-۳۰ ثانیه صرفه‌جویی در هر کار |
| **اولویت صف برای کارهای کوچک** | priority بر اساس حجم (فایل‌های <100MB → صف سریع‌تر) | تجربهٔ کاربران عادی بهتر |
| **پیش‌فرض هوشمند پروفایل** | سورس‌های از پیش فشرده (bitrate پایین) → پیشنهاد r720/small به‌جای balanced | جلوگیری از اتلاف encode بی‌فایده (no-gain) |

### 8.2 کوتاه‌مدت — کد و معماری (پیاده‌سازی‌شده در جلسهٔ سخت‌سازی)

**الف) Transcode بخشی-موازی (Segmented Encoding) — فعال شد ✅**
`ENCORE_SETTINGS_SHARED_WORK_DIR=/media/work` روی web و workerها + فلگ `SEGMENT_ENABLED` در بات: کارهای با مدت ≥ `SEGMENT_MIN_DURATION` (۹۰۰ ثانیه) به‌صورت خودکار با `segmentLength` (۱۰ ثانیه) ارسال می‌شوند و همهٔ ورکرها قطعات را موازی پردازش می‌کنند. پروفایل‌های `repair` و `custom` فعلاً مستثنی هستند (تعامل ورودی/SpEL). اندازه‌گیری تسری واقعی روی کار اصلی کاربر پس از تکمیل آن ثبت می‌شود.

**ب) حذف کپی اضافی منبع — اندازه‌گیری و اعمال شد ✅**
- اندازه‌گیری روی فایل ۳.۹۵GB: `hash+copy جدا` = 32.5s، `تک‌پاس ترکیبی` = **41.8s (کندتر — فرضیه رد شد، I/O تو در تو)**، `هش درجا بدون کپی` = **13.3s** ✅
- اعمال‌شده: هش درجا روی فایل bot-api در زمان ثبت + استفادهٔ مستقیم از مسیر. چون ورکرها volume بردار bot-api را نمی‌بینند، staging کپی شرطی است: پیش‌فرض کپی به /media؛ با `WORKERS_READ_BOTAPI=true` (بعد از mount ro در ورکرها — در compose اعمال شده) کپی حذف می‌شود.
- ذخیره: ~۱۹-۳۰ ثانیه و ۴GB دیسک برای هر فایل بزرگ؛ محافظت دیسک به 2.2× برگشت (کپی شرطی).

**ج) تحویل چندپارته (>۲۰۰۰MB) — پیاده و تست شد ✅**
خروجی‌های بزرگ‌تر از سقف با `ffmpeg segment -c copy` (برش روی keyframe، هر بخش مستقلاً قابل پخش) به پارت‌های زیر `MAX_UPLOAD_MB × 0.85` تقسیم، همه در کانال آرشیو ثبت (schema: `part_index/part_total/split_of` + ایندکس یکتای جدید) و به کاربر با راهنمای join تحویل می‌شوند. Idempotent: retry از روی پارت‌های ثبت‌شده می‌پرد. Unit test روی فایل ۴۲۸MB با سقف ۱۰۰MB: ۵ پارت، همه معتبر، مجموع حفظ‌شده، ۵ ثانیه.
**تست E2E واقعی:** خروجی ۱.۱GB با سقف موقت ۸۰۰MB → ۲ پارت در کانال (پیام‌های ۵ و ۶) → تحویل کامل به چت مالک (method=parts) + راهنمای join ✅

**د) اندازه‌گیری Segmented Encoding — نتیجه: بدون تسریع با ۲ ورکر (پیش‌فرض خاموش)**
| حالت | زمان (محتوای ۴۰ دقیقه 1080p) | نتیجه |
|---|---|---|
| ترتیبی (بدون segment) | 879s | SUCCESSFUL، خروجی ۴۱۴MB سالم |
| segmented (segmentLength=10، ۲ ورکر) | ~۹۰۰s | SUCCESSFUL، خروجی ۴۳۰MB سالم |

سربار seek/join هر قطعه، موازی‌سازی ۲تایی را خنثی می‌کند. فلگ `SEGMENT_ENABLED` روی این سرور **خاموش** است؛ با ۴+ ورکر (یا چند VM) دوباره فعال شود — کد و پیکربندی آماده است.

**هـ) no-gain هوشمندتر:** آستانه via `NO_GAIN_THRESHOLD` (پیش‌فرض ۰.۹۸)؛ هشدار بیت‌ریت پایین روی کارت شروع کار؛ برای منابع no-gain بزرگ‌تر از سقف ارسال، فایل دوباره آپلود نمی‌شود (کاربر فایل خودش را دارد) و فقط توضیح نمایش داده می‌شود.

**و) worker churn**: خروج ورکر پس از خالی شدن صف، رفتار طراحی‌شدهٔ Encore 1.0 است (تأیید از docs و سورس)؛ سیاست restart داکر استخر را همیشه گرم نگه می‌دارد. «ساده‌ترین پیکربندی پایدار» همان است که هست — churn بی‌ضرر و بدون از دست دادن state (همه‌چیز در Redis است).

### 8.3 میان‌مدت — سخت‌افزار (بزرگ‌ترین ضرب)

**گزینهٔ ۱ — GPU با NVENC (توصیه‌شده برای حجم بالا):**
- NVENC (NVIDIA) برای H.264 حدود **۶-۱۰ برابر** و برای HEVC حدود **۴-۶ برابر** سریع‌تر از x264/x265 نرم‌افزاری است
- مسیر عملی: مهاجرت به EC2 `g4dn.xlarge` (4 vCPU + NVIDIA T4، ~۰.۵۲$/ساعت) یا سرورهای GPU ارزان‌تر
- تغییرات لازم: ایمیج worker با ffmpeg دارای `h264_nvenc`/`hevc_nvenc` (بیلد رسمی دوره از ffmpeg استاتیک استفاده می‌کند — باید base image با ffmpeg+NVENC ساخته شود) + پروفایل‌های جایگزین NVENC (کیفیت CRF-محور کمی متفاوت؛ تنظیم `preset p4/p5` و `rc vbr`)
- **نکتهٔ مهم:** یک T4 می‌تواند ۳-۵ استریم NVENC همزمان بچرخاند → معادل چندین برابر کل CPU این VPS

**گزینهٔ ۲ — چند VM توزیع‌شده:**
- دوره ذاتاً توزیع‌شده است: worker های اضافی روی VM های دیگر فقط به Redis مشترک و storage مشترک نیاز دارند
- در چند-VM، storage باید S3 شود (دوره در حالت segment هم به work dir مشترک نیاز دارد → S3 یا NFS بین VM ها)
- هزینهٔ شبکه/حجم‌دانلود بین VM ها را در محاسبه بیاورید

**گزینهٔ ۳ — ارتقای Lightsail فعلی:** 16 vCPU (پلن بالاتر) → تقریباً ۲ برابر throughput با همان کد، بدون تغییر معماری. ساده‌ترین راه.

### 8.4 بهینه‌سازی‌های ریز قابل انجام

| مورد | شرح | اثر |
|---|---|---|
| کپی با hash همزمان | یک پاس خواندن به‌جای دو | ۱۵-۳۰s برای ۴GB |
| حذف کپی وقتی منبع همان مسیر است | الان فقط در retry؛ می‌شود همیشه مستقیم به فایل botapi اشاره کرد و کپی حذف شود (با پاک‌سازی امن) | ۳۰-۹۰s برای فایل‌های بزرگ |
| fingerprint روی GPU/کاهش فریم‌ها | ۸ فریم کافی است؛ هزینهٔ فعلی ناچیز | جزئی |
| direct upload از worker | اگر روزی خروجی مستقیم به کانال برود (بدون برگشت به بات) | حذف یک کپی شبکه‌ای |
| صف اولویت دوگانه | کارهای ادمین/کوچک → queue 0 با اولویت بالا؛ عادی → queue 1 | تجربهٔ بهتر |
| cache بیت‌ریت هدف | نه لازم — محاسبه instantly است | — |

### 8.5 جمع‌بندی پیشنهادی ترتیب اجرا
1. همین هفته: segmented encoding (segmentLength) + ورکر سوم → **~۲-۳ برابر**
2. ماه بعد: پریست‌های سریع‌تر r480/tgcompat + ادغام hash/copy → **+۲۰-۴۰٪**
3. اگر حجم واقعی کاربران بالا رفت: GPU (g4dn) با پروفایل‌های NVENC → **پرش ۵-۱۰ برابری**
4. همیشه: مانیتور `/admin → stats` و shمارندهٔ `bytes_saved` برای تصمیم‌گیری داده‌محور

## 17. بازطراحی محصول (2026-10-29) — جریان ساده کاربر، Tier/VIP، مانیتورینگ

فاز پایدارسازی صبح همان روز همهٔ باگ‌های ممیزی را بست (کرش `STATUS_DONE_NOGAIN`، رفع بن خراب، رقابت cancel، `allow_no_archive` مرده، retry خطای موقت، ضریب دیسک، و…) و سپس بازطراحی اعمال شد:

**جریان کاربر:** فقط `/start` + ارسال ویدیو. کارت اطلاعات (نام/حجم/مدت/رزولوشن) + یک دکمهٔ «فشرده‌سازی» → کاربر عدد ۱ تا ۲۰ (درصد کاهش حجم) می‌فرستد → پروفایل `custom` با بیت‌ریت هدف محاسبه‌شده؛ فلوِورِ بهترین‌تلاش برای سورس‌های از-قبل-فشرده (clamp به `MIN_VIDEO_KBPS` + نکته؛ no-gain = نسخهٔ اصلی + توضیح). دکمهٔ «لغو» روی کارت پیشرفت. همهٔ دستورهای کاربری قبلی (myfiles/stats/settings/language/...) حذف شدند (`handlers/user.py`، `handlers/settings.py` حذف فایل). ادمین‌ها کیبورد کامل پروفایل‌ها + حجم دلخواه را دارند.

**Dedup فازی (migration 005):** لایهٔ جدید برای درخواست‌های درصدی: `(حجم، نام نرمال‌شده، مدت ±۲s)` → نتیجهٔ فشرده‌شدهٔ قبلی همان ویدیو (حتی با بایت‌های متفاوت) بدون encode مجدد تحویل/ملحق می‌شود؛ شمارندهٔ `dedup_fuzzy_reuse`. لایه‌های SHA و pHash سر جایشان.

**تامبنیل گلوبال:** `/admin → 🖼` عکس بفرست → ذخیره در `app_config.global_thumb_path` → روی هر آپلود تازهٔ خروجی (آرشیو، پارت‌ها، تحویل no-gain) اعمال می‌شود.

**Tier/VIP (migration 006):** `users.is_vip` + سه override اختصاصی (حجم/مدت/سهمیه). پیکربندی طبقه در `app_config.limits` (seed از env؛ پیش‌فرض: عادی 4GB/2h/5GB روزانه/2 فعال/10 ساعتی — VIP 4GB/6h/20GB/4/30) با ویرایش زنده از پنل (`tier.key=value`) و مدیریت کاربر (`👤 کاربر`: VIP/بن/سقف اختصاصی). اولویت صف VIP = 60 در برابر 50.

**مانیتور پیوی:** `/admin → 📡` — پیام زنده با نوار پیشرفت هر کار فعال، نشان ⭐ VIP، زمان سپری‌شده؛ رفرش ۵ ثانیه‌ای، توقف خودکار بعد از خالی شدن صف یا دکمهٔ ⏹.

**وب‌پنل:** `127.0.0.1:8090/panel` با `ADMIN_PANEL_TOKEN` (خالی = غیرفعال). فقط-خواندنی: کارت‌های جاب فعال/صف/دیسک/CPU/RAM (psutil)، نمودار روند ۲۴س/۷روز/۳۰روز از `date_bin` روی jobs، تسک‌های در حال اجرا، کاربران اخیر. دسترسی با تونل SSH.

### بهینه‌سازی فشرده‌سازی مبتنی بر منابع (2026-10-31) — کیفیت و سرعت
بر اساس ویکی رسمی ffmpeg (بازهٔ CRF ۱۸–۲۸ و نقش preset در بازدهی) و راهنمای‌های انکد (aq-mode=3 برای صحنه‌های تاریک):

- **نردبان preset در `profiles.preset_for_level`:** درجهٔ ۱–۶ → veryfast (کم-فشرده، سریع‌ترین)، ۷–۱۳ → faster، ۱۴–۲۰ → fast (سرعت ~۲۰٪ کمتر در عوض خروجی محسوساً کوچک‌تر در همان CRF — دقیقاً جایی که کاربر فشرده‌سازی قوی می‌خواهد). کیفیت در CRF ثابت تغییر نمی‌کند (طبق ویکی: preset روی بازدهی اثر دارد نه کیفیت).

- کف کیفیت برای custom همچنان با `MIN_VIDEO_KBPS` و اعتبارسنجی مدت ±۱۵٪ سر جایش است.
